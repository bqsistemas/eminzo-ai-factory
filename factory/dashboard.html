    Cómo funciona la Factory

    Una guía simple para entender qué pasa con cada issue, qué hace cada agente y cómo trabajar con Claude Code o Codex.

    El viaje de un issue, de la idea al merge

    La Factory toma un issue de GitHub con la etiqueta factory y lo acompaña hasta que queda listo para producción. Cada paso deja una evidencia visible y el siguiente comienza solo cuando el anterior está listo.

    1 · IntakeEntiende el pedido y detecta si falta información.
    2 · SpecConvierte la idea en un plan claro y comprobable.
    3 · BuildImplementa el cambio en una rama y prepara el PR.
    4 · GateCorre los checks automáticos antes de revisar.
    5 · ReviewVarios revisores analizan el mismo cambio en paralelo.
    6 · ApproveUn agente reúne los veredictos y recomienda aprobar o corregir.
    7 · MergeEl PR se integra, o queda esperando una decisión humana.
    Idea clave: los agentes hacen el trabajo especializado, pero la Factory mantiene una sola fuente de verdad: el estado del job, sus archivos y el PR.

    Qué hace cada agente

    IntakeLee el issue, resume el problema y pide datos cuando no alcanza para empezar.
    Spec writerDefine alcance, criterios de aceptación y una estrategia de implementación.
    BuilderEscribe el código, ejecuta pruebas y abre o actualiza el PR.
    Security reviewerBusca riesgos de permisos, datos, secretos y validaciones.
    UX reviewerRevisa que el flujo sea claro, accesible y fácil de usar.
    UI reviewerComprueba consistencia visual, estados y adaptación a pantallas.
    Code reviewerAnaliza calidad, errores, regresiones y mantenibilidad.
    ApproverLee todos los veredictos y decide si el job puede pasar a merge.

    Cómo leer los estados

    • Needs info: el issue necesita una respuesta antes de continuar.
    • Spec review: con spec_review activo, el spec está publicado en el issue y espera tu approve-spec o revise-spec.
    • Gate FAIL: una prueba falló; el job vuelve a Build con el motivo.
    • Changes: un reviewer pidió correcciones; el builder vuelve a trabajar.
    • Needs human: hace falta una decisión o acción tuya.
    • Awaiting merge: el PR está listo y espera que una persona haga merge.
    • Merged / Rejected: el job terminó y queda registrado en el historial.

    Cómo usarla

    Primero corré setup una vez por repositorio. Después usá issue <n> para un issue existente o describí una funcionalidad nueva, y run para continuar los jobs pendientes. Elegí los comandos según el asistente que estés usando:

    Claude Code

    • /eminzo-factory setupUna sola vez por repositorio. Ejecutalo dentro de Claude Code o Codex en la terminal de Eminzo, no en el shell: analiza el repo y actualiza factory/project.md.
    • /eminzo-factory runContinúa los jobs locales sin terminar. Solo toma issues nuevos de la cola si run_mode es "queue".
    • /eminzo-factory issue 37Asigna el issue a tu usuario de gh y lo ejecuta. Se rechaza si lo tiene otra persona o si la rama factory/<id> ya existe en el remoto.
    • /eminzo-factory <feature>Crea el issue con el label factory a partir de tu pedido y lo ejecuta.
    • /eminzo-factory xs <request>Igual, pero con el label factory:xs: solo pide el carril XS y el script decide.
    • /eminzo-factory rework 37 [claude|codex]Retoma un job en Needs human con feedback confiable del PR; opcionalmente cambia de proveedor.
    • /eminzo-factory approve-spec 37Aprueba el spec publicado en el issue (su SHA-256) y sigue con el build. Solo cuando spec_review lo pidió.
    • /eminzo-factory revise-spec 37 <notes>Pide cambios al spec con tus notas: el spec writer lo reescribe y se vuelve a publicar para revisión.

    Codex

    • $eminzo-factory runContinúa los jobs locales sin terminar. Solo toma issues nuevos de la cola si run_mode es "queue".
    • $eminzo-factory issue 37Asigna el issue a tu usuario de gh y lo ejecuta. Se rechaza si lo tiene otra persona o si la rama factory/<id> ya existe en el remoto.
    • $eminzo-factory add <feature>Crea el issue con el label factory a partir de tu pedido y lo ejecuta.
    • $eminzo-factory xs <request>Igual, pero con el label factory:xs: solo pide el carril XS y el script decide.
    • $eminzo-factory rework 37 [claude|codex]Retoma un job en Needs human con feedback confiable del PR; opcionalmente cambia de proveedor.
    • $eminzo-factory approve-spec 37Aprueba el spec publicado en el issue (su SHA-256) y sigue con el build. Solo cuando spec_review lo pidió.
    • $eminzo-factory revise-spec 37 <notes>Pide cambios al spec con tus notas: el spec writer lo reescribe y se vuelve a publicar para revisión.

    En Codex, $eminzo-factory es una skill del repositorio. En Claude Code, /eminzo-factory es el comando existente. Ambos usan la misma Factory, el mismo job y las mismas reglas.

    Cuándo intervenís vos

    • Respondé el issue si Intake marca que falta información.
    • Revisá y hacé merge del PR cuando el job quede esperando aprobación.
    • Si pedís cambios, usá el flujo de rework para que el builder reciba comentarios confiables.
    • Usá los detalles de cada tarjeta para leer intake, spec, build, checks y reviews.
    Consejo: no hace falta memorizar los archivos internos. Mirá el tablero como una conversación: cada columna responde “¿qué falta para que este job avance?”.

    Claude y Codex, sin mezclar responsabilidades

    El proveedor elegido queda guardado en cada job. La configuración de factory/config.json decide qué modelo usa cada rol para Claude o Codex, mientras que el gate y las transiciones siguen siendo los mismos.

    Importante: no ejecutes Claude y Codex sobre el mismo job al mismo tiempo. Elegí un asistente por job para evitar que dos sesiones escriban el mismo estado.
